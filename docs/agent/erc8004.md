# ERC-8004 identity + ERC-8021 attribution

Both are required by the hackathon rules ("Your project will only be valid with
an ERC-8004 identity", "Attribution tag must be implemented") and both are
unbackfillable, so they are recorded here with the exact onchain evidence.

## Agent identity (ERC-8004)

| field | value |
|---|---|
| registry | `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` (Celo mainnet) |
| agentId | `10005` |
| owner / agent wallet | `0xDbFe5c4d0256D2459bB216caB905999Ca41bE349` |
| registration tx | `0x9c101fb0dcbfeba0d95c0172b22c996bec949a4d908b4daeaf486c0cd12b2b70` |
| block | `81368442` |
| agentURI | `data:application/json;base64,...` (1701 chars, fully on-chain) |

Metadata is a `data:` URI rather than an IPFS link on purpose: the bytes are the
integrity check, and it cannot rot when a gateway goes down. Shape follows the
current EIP-8004 spec (`type` = the versioned registration identifier,
`services` not `endpoints`, `endpoint` not `url`).

Reproduce or verify:

```bash
.venv/bin/python scripts/register_agent.py --dry-run    # prints gas + metadata
# verify onchain:
#   tokenURI(10005)        -> the data: URI
#   getAgentWallet(10005)  -> 0xDbFe5c4d0256D2459bB216caB905999Ca41bE349
```

`services[]` is written by `scripts/set_agent_services.py` (idempotent — it sends
nothing when the card already matches), and it declares the endpoint that actually
answers:

- `services[0]` = `{"name": "web", "endpoint": "https://celo-invoice-agent.vercel.app"}`
- `x402Support: true`, `active: true`
- `registrations[0].agentRegistry` = `eip155:42220:0x8004A169FB4a3325136EB29fA0ceB6D2e539a432`

The generated mirror of this card is [`erc8004-card.md`](erc8004-card.md) —
written by `scripts/gen_erc8004_doc.py` from `tokenURI(10005)`, so it cannot drift.

Three `setAgentURI` transactions have been sent: `0xa9416d84…9b1e64` added
`services[]`, `0xdcd801a4…adec1` corrected the description, which had claimed invoices settle
*over the x402 facilitator*, and `0xdb1a214f…9584a1` set `x402Support: false` to
match reality. Invoices settle as plain ERC-20 transfers and `bot/verify.py` proves
them from the chain; x402 is what the agent *spends* to buy its sanctions screening,
not what it accepts. `/agent.json` reports the same value as the chain.

## Attribution tag (ERC-8021)

`bot/attribution.py` encodes Schema 0 exactly as `@celo/attribution-tags` → `ox
Attribution.toDataSuffix` does:

```
codes (UTF-8, comma-joined) ‖ codesLength (1 byte) ‖ schemaId 0x00 ‖ marker (16 bytes = 0x8021 × 8)
```

Every transaction we sign appends it to the END of calldata; the EVM discards
trailing bytes so execution is unchanged. Verified on the wire on the
registration tx itself — decoding its calldata yields `['celo_invoiceagent']`
with `codesLen=17, schema=0` and an intact marker.

**Code in use:** `celo_invoiceagent` (a custom code — it tags transactions
immediately, but the Celo attribution dashboard only credits a *registered*
code). Set the code issued at enrolment via `CELO_ATTRIBUTION_CODE` before
sending anything else that should count:

```bash
export CELO_ATTRIBUTION_CODE=celo_xxxxxxxx   # issued code from the program
```

**Not our problem to fix:** Celo's x402 facilitator does not write Schema 2 tags
yet, so x402 settlements carry no attribution. The hackathon credits those via
our PayTo wallet address instead — see below.
